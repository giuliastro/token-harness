# Spike log: live verification (PLAN §2.5)

- Status: in progress
- Started: 2026-07-30
- Machine: Windows 11 Professional 10.0.26200, x64, it-IT, Node 24.13.1

This is the evidence log for the PLAN §2.5 spike. RFC 0007 is written *from* it and is
not written yet: it still needs the OpenCode result, and PLAN §2.5 requires the harness
adapter contract to be "written against RFC 0007, not guessed".

One harness has reached tier 3 end to end — Claude Code with RTK — so PLAN §2.5's first
acceptance criterion is met. The product claim survives.

Everything below was observed on a real machine, not derived from documentation. Where
a result is a negative, the exact invocation is recorded so it can be re-run when a
version changes — PLAN §2.5 question 5 is "which harness versions make tier 3
impossible?", and a negative with no invocation attached cannot answer it later.

## Structural findings

### The hook surfaces are JSON, in two different files

Claude Code keeps hooks inside `~/.claude/settings.json`. Codex keeps them in a
*separate* `~/.codex/hooks.json`, while `~/.codex/config.toml` holds everything else.
So the Codex hook action is `merge-json` on `hooks.json`, not `merge-toml` on
`config.toml`.

This corroborates the finding raised against RFC 0006 §Golden path in the issue-6 PR:
the transcript patches a *marker block* into `~/.claude/settings.json`, which is strict
JSON with no comment syntax. The live file confirms the right family is `merge-json`
appending to `hooks.PreToolUse` — exactly the `append` operation shape implemented in
issue 7.

### Codex records project trust in `config.toml`

```toml
[projects.'C:\Software\SMART7']
trust_level = …
```

PLAN §3.2 asks for "trust-aware verification" without saying what carries the trust.
It is a per-project table keyed by an absolute path, quoted as a TOML *literal* string
because Windows paths contain backslashes. Any future `merge-toml` has to produce that
quoting; a basic-string key would corrupt the path.

### Codex may be installed with no executable at all

Before the CLI was installed, `~/.codex` was fully populated — `config.toml`,
`hooks.json`, `AGENTS.md`, `skills/`, `plugins/` — while nothing named `codex`
resolved on `PATH`. The MSIX app declares no execution alias.

RFC 0002 §Detection forbids inferring from configuration alone, so in that state the
corroborating evidence has to come from the app-package inventory, which yields a name
*and a version* — the version RFC 0002 §Harness versioning requires in every receipt.
PLAN §3.2 does not anticipate this case.

`codex doctor` is a strong detection source once the CLI is present: install method,
package root, resolved executable, version, and the `PATH` entries it found (it lists
both `codex` and `codex.cmd`, the shim pair).

## Canary experiments, Codex CLI 0.146.0

The provider under test is HarnessTrim on `shell.output.reduce`; its receipt is a
`TrimEvent` appended to `.harnesstrim/metrics.jsonl`. Each run used a scratch
directory, a harmless sentinel, and `--json` for machine-readable observation.

| # | Invocation | Command ran? | Receipt? |
| --- | --- | --- | --- |
| 1 | `codex sandbox echo <marker>` | no — `echo` is a shell builtin, `CreateProcessAsUserW` error 2 | — |
| 2 | `codex sandbox node -e "…"` | **yes**, exit 0, correct output | **no** |
| 3 | `codex exec --json -s workspace-write` | no — sandbox denied `pwsh.exe` in `WindowsApps`, error 5 | — |
| 4 | `codex exec --json -s danger-full-access` | **yes**, `aggregated_output` matched the marker | **no** |
| 5 | 4 plus `--dangerously-bypass-hook-trust` | yes | **no** |
| 6 | 5 with a 200-line reducible sentinel | yes | **no** |

The sandbox was disabled and hook trust bypassed only in a scratch directory, with a
sentinel that writes to stdout and touches nothing.

### The sentinel must be an executable, not a shell builtin

Run 1 failed because `echo` is not a program. RFC 0004 §Process policy already
requires an executable plus an argument array for what *Token Harness* runs; run 1
shows the same constraint applies to the sentinel, because the interception point may
execute it without a shell.

### `codex sandbox` executes without traversing the interception point

Run 2 is the trap. A cheap, model-free, deterministic execution path exists, it runs
the command correctly, and no hook fires. A canary built on it would report "the
provider is not intercepting" on a correctly configured machine — a false negative
that looks like a real failure.

### A tier-3 canary costs a model call

Run 3 reported `usage: input_tokens 32016, cached 26112, output 237`. There is no
model-free path to the interception point, so proving tier 3 is not free. RFC 0006
makes `verify` a routine read-only command; running a 32k-token canary on every
invocation is not viable. RFC 0007 has to say how the receipt is cached, or make the
canary explicitly opt-in.

### The agent's own report is not evidence

In run 3 the command failed inside the sandbox and the model still answered `DONE`.
Only the `command_execution` item in the `--json` stream, with its `exit_code` and
`aggregated_output`, distinguished the two. Verification reads the event stream or the
provider receipt, never the assistant's summary.

### The event stream is a second, independent receipt family

`codex exec --json` emits `command_execution` items carrying the exact command string
Codex assembled. For `shell.command.rewrite` that field *is* the evidence of
interception: a rewritten command is visible without asking the provider anything. So
there are two receipt families, and they prove different things:

| Receipt | Source | Proves |
| --- | --- | --- |
| harness event stream | `codex exec --json` | the command that was actually run, so a rewrite is observable |
| provider telemetry | `.harnesstrim/metrics.jsonl`, `rtk gain` | that the provider itself executed |

### `--metrics` records an event per *reduction*, not per invocation

`harnesstrim hook --help` states it: "`--metrics` records a TrimEvent per reduction."
So a minimal sentinel produces no receipt even when the hook fires, because no reducer
matched. PLAN §2.5 asks for a sentinel that is "unambiguous, cheap, and free of side
effects"; for a reducing provider those pull against observability, since the cheapest
sentinel is the one with nothing to reduce. Run 6 used a 200-line repetitive payload
for that reason.

### Open: why the hook does not fire

After runs 4–6 the hook still produced nothing, with the sandbox off and trust
bypassed. The mechanism exists in this build — `findstr` finds `hooks.json`,
`PreToolUse`, `PostToolUse`, and `hook_trust` in `codex.exe` 0.146.0 — so the
remaining candidates are:

1. hooks must be *enabled* as well as trusted; `--dangerously-bypass-hook-trust` is
   documented as running "enabled hooks without requiring persisted hook trust", which
   implies enablement is a separate gate;
2. `codex exec` may not run hooks at all, only the interactive TUI and the app;
3. `~/.codex/hooks.json` may be the app's schema, written by
   `harnesstrim install codex --hook --global`, and read differently by CLI 0.146.

This is not resolved, and the log says so rather than picking the most flattering
explanation.

## Canary experiment, Claude Code + RTK 0.42.0

The provider under test is RTK on `shell.command.rewrite`; its receipt is its own
analytics store, read with `rtk gain`. RTK stores each command in its **rewritten**
form (`rtk tsc`, `rtk read`, `rtk git diff -- …`), so the store is itself evidence of
interception rather than merely of execution.

The sentinel was one read-only git command, run twice through two different tool
families of the same harness, with the counter read before and after each.

| Step | Tool family | `Total commands` |
| --- | --- | --- |
| baseline | — | 2808 |
| `git diff --stat …` | **Bash** | **2809** |
| the same command again | **PowerShell** | 2809 |

**Tier 3 reached, end to end.** An operation was caused, it traversed the interception
point, the provider recorded a receipt, and the receipt was read with no human in the
loop and attributed to exactly one caused operation by the delta. This satisfies PLAN
§2.5's first acceptance criterion, which the Codex work did not.

### The same command through a different tool family is not intercepted at all

The control step is the finding. `~/.claude/settings.json` matches on `"Bash"`, and on
Windows the harness also exposes a **PowerShell** tool. The identical command routed
through it produced no receipt, so the provider never saw it.

RFC 0003 scopes a capability as `<harness>/<tool-family>/<point>/<capability>`, so this
is a real, unowned scope rather than an implementation detail — and it is the *default*
tool family for a Windows user. Two consequences:

1. A coverage figure computed from intercepted operations alone would report this
   installation as fully covered while an entire tool family bypasses the provider.
   RFC 0005's `Coverage` and `Bypassed` lines have to be computed against the harness's
   total tool calls, not against the provider's own event count, or they overstate.
2. `verify` on Windows must check the matcher against the tool families the harness
   actually exposes. A matcher that covers `Bash` and nothing else is a correctly
   installed, correctly verified, and largely ineffective integration.

### Passive and active canaries are different mechanisms

This canary cost nothing: no model call, no tokens. The operation was an ordinary tool
call that the harness was going to make anyway, and the canary only read the receipt
afterwards. The Codex canary cost 32k input tokens because it had to *drive* the harness
from outside.

Those are two mechanisms, and RFC 0007 should name both:

| | Causes the operation | Cost | Answers |
| --- | --- | --- | --- |
| **active** | drives the harness headlessly | a model call | "is interception working right now" |
| **passive** | waits for the user's next real operation | free | "was interception working as of the last observed operation" |

The passive form is what makes a routine `verify` affordable, and it is weaker in a way
that has to be stated rather than hidden: it reports on the past, and it cannot
distinguish "working" from "not exercised yet". A receipt with no observed operation
behind it is not a pass.

## What this already establishes

**A correctly registered hook entry is not evidence that the hook runs.** On this
machine `~/.codex/hooks.json` contains a well-formed `PostToolUse` entry pointing at an
installed provider, and the provider does not run. A `config-only` check would have
reported that integration as present and working.

That is the concrete counterexample behind RFC 0002 §Verification tiers' rule that "a
tier-2 result is never presented as proof of interception" — an argument in the RFC
until now, and a demonstrated fact from here on.
