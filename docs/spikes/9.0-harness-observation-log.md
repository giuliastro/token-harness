## Hermes Agent v0.19.0

### Configuration files

| Scope | Path | Parser |
| --- | --- | --- |

| user, plugins | `~/.hermes/plugins/<name>/` | directory per plugin; each has `plugin.yaml` + Python |
| user, env | `~/.hermes/.env` | dotenv |
| runtime env | Hermes gateway process environment | environ of the running process |

No project-scoped file for Hermes exists on this machine. There is also a `~/.hermes/hooks/`
directory, but on this installation it is **empty** (`drwx------`, created 2026‑03‑19); Hermes'
interception mechanism is the plugin surface, not that directory.

### Enablement — readable, no separate hook state

The `~/.hermes/config.yaml` plugin section is fully readable from outside the harness:

```yaml
plugins:
  disabled: []
  enabled:
    - google_meet
    - rtk-rewrite
    - harnesstrim
  entries:
    harnesstrim:
      allow_tool_override: false
```

There is no trusted‑hash or separate enablement‑state file in the namespace — unlike the
Codex `trusted_hash` finding in Phase 2.5. `hermes plugins list` confirms the effective
state (`harnesstrim … enabled user 0.0.1`).

### Interception point — plugin hook, not a command hook

Hermes plugins register callbacks on a fixed hook set declared in
`~/.hermes/hermes-agent/hermes_cli/plugins.py` (line 135):

```python
VALID_HOOKS = {
    "pre_tool_call", "post_tool_call", "transform_terminal_output",
    "transform_tool_result", "transform_llm_output",
    "pre_llm_call", "post_llm_call", "pre_verify",
    "pre_api_request", "post_api_request", "api_request_error", "on_session_start",
}
```

The HarnessTrim plugin registers exactly one of them
(`~/.hermes/plugins/harnesstrim/__init__.py`):

```python
def register(ctx):
    ctx.register_hook("transform_tool_result", on_tool_result)
```

The hook fires after each tool call in `~/.hermes/hermes-agent/hermes_cli/model_tools.py`
(around lines 1382–1412), gated on `has_hook("transform_tool_result")`: fail‑open, the first
callback returning a string wins, non‑string returns are ignored. A real configured entry is
the combination of the plugin files plus the `harnesstrim` line in the `enabled` list above.

### Tool families — the shell family is inside the candidate set

The plugin only considers a closed tool set:

```python
REDUCER_TOOLS = frozenset({"terminal", "read_file", "web_extract",
                           "search_files", "browser_snapshot", "vision_analyze"})
```

`terminal` is the shell‑executing family and it is in the set, so a shell command is not
routed around the transform hook the way Claude Code's PowerShell family bypasses a `"Bash"`
matcher (Phase 2.5 finding). Whether Hermes exposes any *other* shell‑capable family outside
`REDUCER_TOOLS` was not observed — open question 1.

### Recording — a real receipt exists

`~/.hermes/harnesstrim-metrics.jsonl` exists, is live, and is the receipt evidence in this
system:

```
$ wc -l ~/.hermes/harnesstrim-metrics.jsonl
111
$ tail -1 ~/.hermes/harnesstrim-metrics.jsonl
{"ts": "2026-08-03T10:21:16.242682+00:00", "harness": "hermes", "tool": "terminal",
 "reducer": "generic-text-slim", "beforeChars": 23184, "afterChars": 22994}
```

(one JSON object per line — the display above is wrapped for readability)

Each line is a `TrimEvent`‑family object: `ts`, `harness`, `tool`, `reducer`, `beforeChars`,
`afterChars`. The path is fixed by the plugin source (`__init__.py` line 44):

```python
METRICS_PATH = Path(os.environ.get("HERMES_HOME", str(Path.home() / ".hermes"))) \
    / "harnesstrim-metrics.jsonl"
```

The plugin defaults are conservative (`mode: dryrun`, `minLength: 400`, `telemetry: False`,
opt‑in), but the running gateway carries the actual setting in its own process environment
(`/proc/<gateway_pid>/environ`):

```
HARNESSTRIM_MODE=active
HARNESSTRIM_MINLENGTH=150
HARNESSTRIM_TELEMETRY=true
```

and `_load_config()` reads every config key from the environment (`HARNESSTRIM_<KEY>`). So on
this machine the plugin runs **active with telemetry on**, and the 111‑line JSONL is the
observable record of recent reductions (last event `2026-08-03T10:21:16Z`).

**Tier for Hermes: the receipt exists, so the passive canary is reachable.** An attributed
one operation → one receipt delta was not run during the spike; that closing delta is the
remaining step before a tier‑3 claim. Until then Hermes sits above `config-only` because the
receipt is real, machine‑readable, and independent of the config — but the final row in the
tier table is labelled accordingly.

## Pi v0.83.0

### Configuration files

| Scope | Path | Parser |
| --- | --- | --- |
| user | `~/.pi/agent/settings.json` | JSON |
| user, trust | `~/.pi/agent/trust.json` | JSON |
| user, sessions | `~/.pi/agent/sessions/*.jsonl` | JSONL |
| user, extensions | `~/.pi/agent/extensions/` | directory scan |
| project | `<project-root>/.pi/` and `<project-root>/.pi/extensions/` | directory scan |

`~/.pi/agent/settings.json` has no extensions section — only theme, defaultProvider,
defaultModel, defaultThinkingLevel, lastChangelogVersion. The Pi runtime (`dist/config.js`,
`CONFIG_DIR_NAME = ".pi"`) resolves the agent dir to `~/.pi/agent`. `trust.json` is a
per‑project trust table (`{"//home/giulio/Software/…": true}`) — a trust record with no
hook‑enable semantics.

### Interception point — an extension script, no handle needed

Pi loads extensions from the extension dirs (`dist/core/extensions/loader.js`:
`<cwd>/.pi/…` project first, then `~/.pi/agent/…` user) and after every tool emits
`tool_result` (`agent-session.js` → `emitToolResult`). An extension handler is chain‑shaped:
it may return a patch `{ content }` that replaces what the model sees.

The HarnessTrim extension is at `~/.pi/agent/extensions/harnesstrim/index.ts` (2808 bytes)
and a second copy at `~/.pi/extensions/harnesstrim/harnesstrim.ts` (2757 bytes). Both:

- shell out `spawnSync("harnesstrim", ["reduce", "--min-length", N])`, 30 s timeout,
  fail‑open;
- read `HARNESSTRIM_MODE` (default **dryrun**; `HARNESSTRIM_MINLENGTH` default 400:
  the extension does NOT reduce unless active);
- in dryrun it logs to stderr and returns the content unchanged; the `[harnesstrim` marker
  stops re‑slimming already‑slimmed output.

The user‑scope copy is byte‑identical to the bundled asset in harnesstrim 0.0.6:

```
7ee88d2ee19f3ed5a841136153b4234e9f107127837a5e3d6f7f564545f0f9a3  ~/.pi/agent/extensions/harnesstrim/index.ts
```

The project-scope copy is **not** byte‑identical
(`6047ad35c4f9ddac1d517fdb238705ab17fea3f04025d35e7d22246390e08a8a`), differing only in a
comment and a type cast. Which HarnessTrim version installed it is open question 2.

### Enablement

Presence == enabled. There is no state gate: the loader is a directory scan and the
`.installed` marker literally says “Remove this directory to uninstall.” Trust lives in a
separate JSON file but is not a hook‑enable gate.

### Recording

**No. There is no receipt on disk.** The extension returns a patched content in active mode
and writes no metrics file; `~/.hermes/harnesstrim-metrics.jsonl` is a Hermes‑specific
artifact, and Pi does not write to it. Therefore **tier: config‑only, which is the expected
answer, not a disappointment.** A level‑3 canary would have to drive the model headlessly and
inspect what the model actually saw — the Phase 2.5 “costs a model call” result, with no
receipt to read. Nothing in the fixture lets a deterministic probe observe a reduction
without a model call.

### HarnessTrim installer — Pi write set

```
harnesstrim install pi [dir]            Install Pi tool_result extension (dry-run)
                          --apply        Actually write the change
```

The user‑scope write on this machine is `~/.pi/agent/extensions/harnesstrim/`
(`index.ts` + `.installed`), and the marker text records exactly `harnesstrim install pi
--apply`. No enablement entry is written — presence is the enablement. The extraneous
project‑scope copy (`~/.pi/extensions/…`) also carries the same `.installed` marker.

## OMP v17.2.4

### Configuration files

| Path | Parser | Note |
| --- | --- | --- |
| `~/.omp/agent/config.yml` | YAML | `providers: {}`, `modelRoles.default: openai-codex/gpt-5.6-terra:medium`, `dev.autoqaConsent: granted` |
| `~/.omp/agent/hooks/pre/` | directory of `.ts` files | `rtk-rewrite.ts` |

| `~/.omp/agent/sessions/`, `~/.omp/{cache,logs,natives,puppeteer,run,autoqa.db}` | — | runtime state |

### Interception point — “hooks/pre|post” as discovered files

Two hand‑written hooks exist, dated 2026‑07‑28, with **no** `.installed` marker:

- `~/.omp/agent/hooks/pre/rtk-rewrite.ts` (995 bytes) — pre‑exec bash rewriter;
- `~/.omp/agent/hooks/post/harnesstrim.ts` (1604 bytes) — post tool‑result reducer, the same
  `spawnSync("harnesstrim", ["reduce", "--min-length", N])` pattern, but the default
  `HARNESSTRIM_MODE` is **active** (opposite of Pi's dryrun), fail-open, and it never replaces
  content with a longer result.

The OMP binary (v17.2.4) itself carries the hook strings: `hooks/pre/*.ts`, `hooks/post/*.ts`,
`emitToolResult`, a `.claude/hooks/pre|post` compatibility reference, and `hookCapability`.

### How hooks are actually run — not yet observed

The files exist and the binary name‑drops the mechanism, but **no execution was observed**:
no receipt, no log, no stderr from either hook was found, and OMP's config has no obvious
hook‑enable/toggle entry. This is exactly the PLAN §9.0 “config‑only is the expected answer”
case. Nothing turns “a file that exists” into “the running harness executes it”
(“declared but not active” — the Phase 2.5 lesson).

### HarnessTrim installer — OMP write set

**None.** `harnesstrim install --help` (0.0.6) lists `claude`, `codex`, `hermes`, `opencode`,
`pi` — there is **no `install omp`**, and the CLI contains no `adapter-omp` assets. If Token
Harness must configure OMP, it cannot delegate to the HarnessTrim installer as bundled and
would have to write the hook file itself (the write‑set question becomes open question 4).
