# Token Harness 0.1.16 — Forward-compatible managed runtimes

`0.1.16` stops treating every new harness or optimizer release as something Token Harness must be manually re-approved for before it can work.

## What changed

- **Future versions are no longer blocked just because they are new.** Compatibility rows are historical evidence, not a runtime permission list.
- **Runtime capability wins.** A newer provider can be managed when the installed build still exposes the integration surface Token Harness needs.
- **Updates verify what actually became active.** After an update, Token Harness re-reads the executable resolved on PATH and checks the required capability contract. If the old binary is still active or the new release changed the contract, the update fails and rolls back.
- **HarnessTrim follows its machine-readable contract.** HarnessTrim 0.3+ supplies its own capability declaration and skill artifact digests. Token Harness uses those instead of hard-coding each new release.
- **Modern HarnessTrim failures are explicit.** A future HarnessTrim release that drops or changes the digest contract is treated as capability drift; Token Harness does not silently reuse 0.0.7 digests.
- **mcptoon, GitNexus and Headroom are latest-forward above their supported floors.** Their managed integrations remain available while the required CLI surfaces can still be observed.
- **Benchmark evidence stays conservative.** Runtime compatibility with a future version does not automatically inherit old benchmark or performance claims.

## Safety

The change does not bypass the existing safety model. Managed changes still use preview/approval, ownership checks, containment/write-set checks, drift detection, backups, rollback and post-apply verification.

## Upgrade

```sh
npm install --global token-harness@latest
token-harness
```
