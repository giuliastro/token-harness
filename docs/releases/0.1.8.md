# Token Harness 0.1.8 — action-first onboarding and clearer daily use

`0.1.8` turns the simplified onboarding introduced in 0.1.7 into a much clearer day-to-day experience. The CLI and local dashboard now focus on the only question a user should need to answer: what should I do now?

## What changed

- **Action-first dashboard.** The local UI now uses clear `READY`, `READY WITH LIMITATIONS`, `ACTION NEEDED`, and `SETUP NEEDED` states instead of exposing internal details first.
- **Only relevant harnesses stay prominent.** Missing harnesses are hidden, while secondary detected tools move into progressive disclosure.
- **Active setup determines health.** An unused secondary harness such as Pi no longer downgrades the primary state of an otherwise healthy configuration.
- **Clear steady state.** When everything is working, Token Harness explicitly tells you to keep using Claude Code, Codex, or OpenCode normally. There is no artificial command loop to keep running.
- **Empty really means empty.** A machine with no usable pipeline is no longer described as healthy just because there is currently nothing to change; it is correctly shown as needing setup.
- **Cleaner optimizer presentation.** The active optimizer is summarized compactly instead of being buried among large provider cards.
- **Safer update messaging.** Legacy user-owned integrations can be recognized read-only, while unreviewed provider upgrades are conservatively kept on the installed version and reported as normal deferred state rather than a developer-facing error.
- **Better recommendation evidence.** Zero-byte or otherwise non-causal context evidence is no longer used to justify optimization recommendations.
- **Stronger first-run guidance.** `setup` distinguishes genuinely broken integrations from versions that are merely newer than the recorded compatibility evidence.
- **Explicit privacy contract.** The dashboard remains loopback-only and read-only, cannot modify configuration, and clearly states that it does not send data anywhere.
- **Responsive UX.** Light/dark presentation, keyboard focus, touch targets, and reduced-motion behavior were tightened for desktop and mobile-sized browser windows.
- **README aligned with real usage.** The documentation now explains what happens after installation, what `setup` and `ui` are for, and what normal daily use looks like once Token Harness is healthy.

## Recommended first run

```sh
npm install --global token-harness@latest
token-harness setup
token-harness ui
```

Once the dashboard reports that the setup is ready, go back to your coding agent and use it normally. Token Harness is the efficiency layer around that workflow, not another shell you need to keep interacting with.

## Upgrade

```sh
npm install --global token-harness@latest
```

Then run `token-harness setup` once to verify the local configuration and `token-harness ui` whenever you want the compact status view.

## Safety

Token Harness remains conservative about configuration changes. Unsupported or unrecorded provider/integration combinations are not silently upgraded, legacy ownership is not invented, and the local dashboard remains non-mutating.

## Why this release matters

The biggest usability gap after 0.1.7 was not capability but comprehension: a new user could install the tool successfully and still struggle to tell whether it was working, what it had done, and what to do next. `0.1.8` makes those answers explicit while preserving the same conservative compatibility and privacy boundaries.
