# Token Harness 0.1.6 — quota-aware cross-harness release

`0.1.6` is the first Token Harness release where the quota-aware Claude Code/Codex work is usable as one end-to-end workflow rather than as separate observability primitives.

## What changed

- **Conservative cross-harness scheduling.** `token-harness schedule` evaluates whether to stay on the current harness or recommend Claude Code ↔ Codex based on independently observed five-hour/weekly pacing, task class, empirical candidate-quality evidence and transfer evidence.
- **Live pacing without quota fiction.** Unknown pace fields can be hydrated from the same `budget` observations used elsewhere in Token Harness. Cached/stale/ambiguous evidence remains unknown, and Claude/Codex quota percentages are never converted into a shared unit.
- **Empirical quality evidence.** Project-scoped benchmark receipts can hydrate candidate quality only for the exact harness and task class. Conflicting or missing evidence stays unknown.
- **Measured transfer evidence.** `transfer` evaluates an explicit stay-vs-switch benchmark pair; `transfer-record` persists an immutable, project-scoped receipt. Historical transfer receipts can inform later scheduling only when route and task class match and every attributable known verdict agrees.
- **Bounded compact handoffs.** `handoff` creates a deterministic objective/decisions/files/validation/unresolved/next-action payload under a hard UTF-8 byte ceiling instead of copying a transcript.
- **Exact current handoff cost.** `schedule --handoff-file <path>` measures the actual current handoff byte length at the host boundary. The content is not decoded, logged or persisted by the scheduler.
- **Benchmark matrix.** Completed local benchmark pairs can be grouped by task class and evidence strength without summing unrelated backend percentages or inventing a composite score.
- **Stronger release gate.** CI now exercises the cross-harness entrypoints from both the self-contained bundle and the installed npm tarball on Windows, macOS and Linux.

## Safety boundaries

This release is deliberately advisory:

- it never launches or switches a harness automatically;
- it never treats local token counts as subscription quota;
- it never compares Claude and Codex percentages as if they represented equal work;
- it never turns missing, cached, stale, ambiguous or conflicting evidence into a positive recommendation;
- it never crosses into paid API routing implicitly;
- explicit evidence supplied by the user wins over historical hydration.

A `switch` recommendation therefore requires positive evidence; otherwise the result is `stay` or `insufficient-evidence` with reasons.

## Quick path

```sh
npm install --global token-harness

token-harness budget
token-harness optimize --task hard --profile balanced

token-harness schedule \
  --current claude \
  --candidate codex \
  --task-class hard
```

When local empirical receipts exist, `schedule` hydrates the evidence it can prove. For an in-progress task, create the handoff first and let the scheduler measure the exact file:

```sh
token-harness handoff \
  --objective "finish the current task" \
  --next-action "continue implementation and validation" \
  > handoff.md

token-harness schedule \
  --current claude \
  --candidate codex \
  --task-class hard \
  --handoff-file handoff.md
```

See the README for the complete benchmark → transfer → transfer-record workflow.

## Why this is still 0.1.x

The quota-aware release gate is usable, but the broader `0.2.0` contract remains intentionally open: wider managed-harness lifecycle coverage, additional provider channels, goal-based pipeline profiles and broader empirical matrices are separate milestones. `0.1.6` does not rename those future gates as completed.
