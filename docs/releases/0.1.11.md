# Token Harness 0.1.11 — Optimization Stack Manager, safer updates and evidence-driven candidates

`0.1.11` packages the substantial work merged after `0.1.10`. Token Harness has evolved from a collection of optimization controls into a clearer **Optimization Stack Manager** for Claude Code and Codex: it manages proven optimizers, evaluates additional components without prematurely enabling them, explains what is active, and keeps savings claims tied to evidence Token Harness can actually attribute.

## What changed

- **Optimization Stack Manager direction.** The guided product now separates the current managed stack from candidate optimizers, shows what is active and what can safely be changed, and keeps advanced implementation detail out of the normal user path.
- **Simpler guided UI.** Dashboard, Setup and Results were reorganized around the questions users actually have: what is enabled, what Token Harness can improve, whether it worked, and what the measured benefit is. Loading behavior, action feedback, modal handling and candidate comparison were hardened as part of the same work.
- **Managed RTK + HarnessTrim stack.** Ownership, compatibility, verification, update and rollback behavior were tightened. Provider updates fail closed outside reviewed versions/surfaces, and Windows now has a live RTK release-replacement smoke gate in normal CI.
- **Safer update and rollback mechanics.** Package-manager inventory, provider update channels, transactional state, verification scope and rollback/uninstall paths gained additional regression coverage so brownfield state and unrelated user configuration remain protected.
- **Candidate evaluation framework.** mcptoon, GitNexus and Headroom can be evaluated through explicit promotion gates instead of becoming normal providers merely because an integration primitive exists. Paired campaigns track quality, local evidence, timing, activation and compatibility separately.
- **mcptoon 0.7.10 reviewed candidate path.** Token Harness now has an exact-version managed lifecycle slice, passive activation evidence, exact Linux compatibility rows for Codex 0.152.1 and Claude Code 2.1.269, project-maturity review, and privacy-bounded manifest-footprint evidence derived from the local schema cache. Future mcptoon versions do not inherit this evidence automatically.
- **No invented mcptoon savings.** The manifest footprint records aggregate JSON-versus-compact byte size for the same local cached tool set, but it is deliberately not treated as model-visible token, quota or subscription savings. Persisted evidence is validated fail-closed before campaign reporting.
- **GitNexus managed lifecycle primitive.** The reviewed Claude Code MCP slice can own only the `mcpServers.gitnexus` entry transactionally, preserve unrelated state and refuse ambiguous brownfield ownership. Codex remains excluded until equivalent surgical ownership is available.
- **Headroom candidate smoke.** Exact Headroom 0.37.0 can be observed passively for benchmark capability without activating its wrapper/proxy behavior. Its broader context ownership still requires stronger evidence before promotion.
- **Combined-stack and promotion readiness.** Candidate readiness now distinguishes benchmark capability, selection evidence, activation verification, managed lifecycle, compatibility/reversibility, project maturity, combined-stack validation and the additional admission required for broad context owners.
- **Context-cost and benchmark tooling.** Candidate attribution, benchmark campaigns, context-cost reporting and stack review gained explicit evidence boundaries so local measurements are not silently converted into provider quota or monetary claims.
- **README and onboarding refresh.** Installation and normal use were simplified, including AI-assisted onboarding guidance and clearer distinction between everyday actions and advanced diagnostics.

## Upgrade

```sh
npm install --global token-harness@latest
```

Then launch Token Harness normally:

```sh
token-harness
```

Claude Code and Codex continue to be launched normally. Token Harness observes and manages only the surfaces covered by its reviewed policies; candidate components remain gated until their independent promotion evidence is sufficient.

## Safety and measurement boundaries

Token Harness continues to treat Claude/Codex subscription allowance, provider percentages, local token estimates, wall-clock measurements and mechanism-specific byte reductions as different evidence types. Missing evidence remains missing rather than being converted into an estimate.

`0.1.11` does **not** promote mcptoon, GitNexus or Headroom into the normal provider registry. Their new lifecycle and benchmark primitives are there to make an eventual promotion decision evidence-driven and reversible, not automatic.
